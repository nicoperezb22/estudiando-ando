Lección 1 · HTTP y APIs

Anatomía de una request HTTP

Qué pasa realmente cuando un HTTP Request node de n8n "habla" con Gmail o Sheets — y cómo elegir el método correcto.

Cada vez que FastPass lee un correo o escribe una fila en Sheets, en algún lugar de n8n se dispara esto: un programa (n8n) le pide algo a otro programa (la API de Gmail o de Sheets), usando un formato de mensaje fijo llamado HTTP. Ese formato es el mismo sin importar si hablás con Gmail, con Mercado Pago o con una API que vos mismo escribas el día de mañana. Aprenderlo una vez te sirve para siempre.

Las dos mitades de la conversación

Toda interacción HTTP tiene exactamente dos partes: una request (lo que el cliente pide) y una response (lo que el servidor contesta). Así se vería si n8n le pidiera a Gmail los últimos correos:

Request (n8n → Gmail)
GET /gmail/v1/messages
Headers: Authorization: Bearer <token>
Body: (vacío)
↓ el servidor procesa y contesta ↓
Response (Gmail → n8n)
Status: 200 OK
Headers: Content-Type: application/json
Body: { "messages": [ { "id": "18f3a2" }, ... ] }

Cuatro piezas para memorizar, dos por lado:

En la requestEn la response
Método + URL — qué querés hacer, y sobre qué recursoStatus code — si salió bien, mal, y por qué
Headers — metadata (auth, formato de datos)Headers — metadata de la respuesta
Body — los datos que mandás (si hace falta)Body — los datos que te devuelve
Dónde lo ves en n8n: el HTTP Request node tiene un campo Method (el verbo), un campo URL, y pestañas separadas para Headers y Body. Es literalmente el mismo diagrama de arriba, con inputs.

Los métodos: qué le estás pidiendo al servidor

El método es la parte que más se presta a confusión, así que la clave no es memorizar la lista — es entender qué efecto tiene cada uno sobre el recurso.

MétodoQué le pedís al servidor¿Repetirlo cambia el resultado?
GET"Dame información." No modifica nada.No — podés repetirlo mil veces sin efecto (idempotente).
POST"Creá algo nuevo." Manda datos en el body.Sí — cada repetición suele crear un recurso nuevo.
PUT"Reemplazá esto por completo." Mandás el objeto entero.No — mandarlo 5 veces da el mismo resultado que 1 vez.
PATCH"Modificá solo esta parte." Mandás solo lo que cambia.Depende de la API — en general se trata como si no.
DELETE"Borrá esto."No — borrarlo de nuevo no tiene efecto adicional.

Idempotente es la palabra técnica para "repetirlo no cambia nada más". Es útil porque te dice qué métodos son seguros de reintentar automáticamente si una request falla por timeout — con POST hay que tener cuidado (podrías crear el mismo pedido dos veces); con GET, PUT o DELETE, no.

Ejemplo FastPass: leer correos nuevos de Gmail → GET. Agregar una fila a Sheets con un pedido nuevo → POST. Si algún día FastPass tuviera que corregir un pedido ya cargado → PATCH (solo el campo que cambió) en vez de reescribir la fila entera.

Ejemplos reales, fuera de n8n

n8n te esconde el detalle. Para que se te grabe de verdad, mirá estos tres casos con APIs públicas reales — dos los podés probar ahora mismo.

1. GitHub API — GET, sin autenticación
GET https://api.github.com/repos/n8n-io/n8n
↓
Response
Status: 200 OK
Body: { "full_name": "n8n-io/n8n", "stargazers_count": 48000, "language": "TypeScript", ... }

Pegá esa URL directo en tu navegador — es pública, no hace falta token, y el navegador te muestra el JSON tal cual llega.

2. JSONPlaceholder — POST, API hecha para practicar
POST https://jsonplaceholder.typicode.com/posts
Body: { "title": "mi primer post", "body": "probando POST", "userId": 1 }
↓
Response
Status: 201 Created
Body: { "title": "mi primer post", "body": "probando POST", "userId": 1, "id": 101 }

JSONPlaceholder existe específicamente para esto: podés armar un HTTP Request node en n8n apuntando ahí y probar GET/POST/PUT/PATCH/DELETE sin miedo a romper nada — no guarda de verdad lo que le mandás, pero contesta como si fuera una API real.

3. OpenWeatherMap — GET con parámetros en la URL
GET https://api.openweathermap.org/data/2.5/weather?q=BuenosAires&appid=TU_API_KEY

Este caso muestra algo que no vimos todavía: un GET puede llevar información extra como parámetros en la URL (todo lo que va después del ?) para filtrar qué querés — acá, qué ciudad. No hace falta body para eso.

Poné a prueba el concepto

Para cada escenario, elegí el método HTTP correcto. No hay trampa — pensá en el efecto sobre el recurso, como en la tabla de arriba.

Escenario 1
Un cliente completa el formulario de FastPass para pedir un producto nuevo en la sala VIP.
Escenario 2
n8n necesita traer la lista de pedidos pendientes desde Google Sheets, sin modificar nada.
Escenario 3
Un pedido ya cargado tiene mal solo el número de mesa, y querés corregir únicamente ese campo.
Escenario 4
Un pedido se canceló y hay que sacarlo por completo del sistema.
Escenario 5
Tenés el objeto completo y actualizado de un pedido (todos sus campos) y querés que reemplace por completo a la versión vieja.
