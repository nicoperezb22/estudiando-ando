Lección 5 · HTTP y APIs

Tu primera request autenticada

JSONPlaceholder no pedía nada. Casi todas las APIs reales sí. Hoy le demostrás a una API quién sos — y rompés la request a propósito para aprender a diagnosticar un 401.

Vas a usar la API de GitHub (tenés cuenta, ¿no? si no, crearla es gratis y sirve para tu portafolio igual). Tiempo estimado: 10 minutos. Herramienta: el HTTP Request node de n8n.

¿En qué header viaja normalmente el token?

Paso 1 — Probar SIN token (para ver el error)

Pegá esto en la barra del navegador:

GET sin credenciales
GET https://api.github.com/user
¿Qué esperás? (clic para revelar)

Un 401 con un mensaje tipo "Requires authentication". Según la doc de GitHub, /user devuelve "el usuario autenticado" — si no le decís quién sos, no tiene a quién devolver. Comparalo con /repos/n8n-io/n8n de la Lección 1: ese es público y no pide nada.

Paso 2 — Conseguir un token

  1. En GitHub: Settings → Developer settings → Personal access tokens.
  2. Generá un token (GitHub recomienda los fine-grained; para esta prueba alcanza con el mínimo de permisos y una expiración corta, por ejemplo 7 días).
  3. Copialo — GitHub te lo muestra una sola vez.
El token es una contraseña. Quien lo tiene actúa como vos. No lo pegues en el chat conmigo, en un repo, ni dentro de un workflow que exportes. En n8n va en Credentials, que es justamente para eso (lo hacemos en el paso siguiente). Si alguna vez se te escapa uno, lo revocás en la misma pantalla donde lo creaste.

Paso 3 — La request autenticada en n8n

En un HTTP Request node:

  1. Method: GET
  2. URL: https://api.github.com/user
  3. Authentication: Generic Credential Type → Header Auth
  4. Creá una credencial nueva. Name: Authorization · Value: Bearer TU_TOKEN (la palabra Bearer, un espacio, y el token)

Alternativa más cómoda: el dropdown también tiene Bearer Auth, donde cargás solo el token y n8n agrega Bearer por vos. Es lo mismo por debajo — ver la referencia de tipos de autenticación.

Es literalmente el header de la Lección 3, armado por n8n. Según la doc de n8n, Header Auth es solo eso: un Name y un Value que viajan en cada request.

¿Qué esperás ahora?

200 OK, con un JSON de tu propio perfil: login (tu usuario), id, avatar_url, public_repos, etc. Fijate que la misma URL que antes te dio 401 ahora da 200: lo único que cambió es el header Authorization.

Paso 4 — Rompelo a propósito

Editá la credencial y cambiá un solo carácter del token. Ejecutá de nuevo. Deberías ver un 401 otra vez.

Esto es lo más útil de la lección: un 401 casi nunca se arregla tocando la URL, el método o el body. Es un problema de credenciales — token mal copiado, vencido, revocado, o sin el prefijo Bearer. Cuando FastPass te tire un 401, ya sabés dónde mirar.

Dos matices reales que documenta GitHub: (1) si tu token es válido pero no tiene permiso para lo que pedís, podés recibir 403 o incluso 404 — GitHub a veces responde 404 para no confirmar que un recurso privado existe. (2) Si fallás la autenticación muchas veces seguidas, GitHub te rechaza todos los intentos con 403 por un rato. O sea: un 404 no siempre significa "no existe", y un 403 no siempre significa "sin permiso". Las categorías guían, la doc de cada API decide. (Fuente: GitHub Docs — Authenticating to the REST API).

El mismo patrón, en otras APIs

Lo que acabás de hacer se repite casi igual afuera. Por ejemplo, las APIs de OpenAI (que vas a usar con el SDK/LangChain) y de Mercado Pago (para EVACAKES) usan también Authorization: Bearer <token> — confirmalo en su doc cuando llegues, pero la idea es la misma: obtenés un token en el panel del servicio, lo guardás como credencial, y viaja en ese header. Aprendiste el patrón una vez.
