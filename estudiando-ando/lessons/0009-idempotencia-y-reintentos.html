Lección 9

Idempotencia y reintentos: por qué un POST duplicado te puede romper todo

La Lección 1 ya nombraba la palabra "idempotencia" al lado de cada método, pero pasó de largo. Ahora que sabés armar una request completa (método + URL + headers + body), esto deja de ser trivia y se vuelve una decisión de diseño real: ¿qué pasa si la misma request se ejecuta dos veces?

Idempotente = ejecutarla 1 vez o 10 veces produce el mismo estado final en el servidor. No significa "no hace nada", significa "no importa cuántas veces se repita por error".

1. La tabla que tenés que memorizar

Método¿Idempotente?Por qué
GETSíSolo lee, nunca cambia nada.
PUTSíReemplaza el recurso entero por el mismo valor — repetirlo dos veces deja el mismo resultado que una.
DELETESíBorrar algo ya borrado no cambia nada (aunque la segunda vez te devuelva 404 en vez de 200).
PATCHDependeSi el cambio es {"estado": "activo"}, sí. Si es {"cantidad": "+1"} (incrementar), NO — cada repetición suma de nuevo.
POSTNoPor definición crea algo nuevo cada vez que se ejecuta. Dos POST = dos recursos creados.

2. El escenario real que te puede pasar en FastPass

n8n manda un POST para anotar a un pasajero en la lista de espera. La red falla justo cuando la respuesta vuelve (la request sí llegó y se procesó, pero la confirmación no). n8n interpreta "no hubo respuesta" y, si tiene un reintento automático configurado, manda el mismo POST de nuevo. Resultado: el pasajero queda anotado dos veces en la cola.

Esto no es hipotético — es exactamente el motivo por el que las APIs de pago (Stripe, Mercado Pago) exigen un Idempotency-Key en el header de cada POST: un ID único que vos generás por operación, para que el servidor sepa "este POST ya lo procesé, aunque me llegue de nuevo, no lo repito". No toda API lo soporta, pero es el patrón estándar de la industria para resolver justo este problema.

3. Qué hacer cuando la API no tiene Idempotency-Key

  • No reintentar POSTs automáticamente sin verificar antes si ya se creó (ej. un GET que chequee "¿este pasajero ya está en la cola?").
  • Si podés elegir el diseño, preferir PUT sobre POST cuando el cliente puede generar el ID del recurso de antemano (ej. PUT /pasajeros/{telefono} en vez de POST /pasajeros) — así un reintento es inofensivo.
  • En n8n: revisar la config de Retry On Fail del HTTP Request node — está pensada para errores de red transitorios, no es gratis para un POST no protegido.
