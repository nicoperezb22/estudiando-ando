Lección 3 · HTTP y APIs

Headers: metadata, y por qué casi todo pide un token

El header que le explica al servidor qué le estás mandando, y el header que le prueba quién sos. Los dos bugs más comunes de "por qué me tira error" viven acá.

Desde la Lección 1 venimos mencionando los headers como una de las tres piezas de toda request/response, junto al método/status y al body. Hoy los abrimos.

¿Qué es un header, en criollo?

Un header es un par clave: valor que viaja pegado a la request o a la response, separado del body. No son "los datos" — son información sobre los datos, o sobre quién los manda. Pensalo como el sobre de una carta: el body es la carta, los headers son lo que está escrito afuera del sobre (remitente, tipo de envío, prioridad).

HeaderPara qué sirve
Content-Type"El body que te mando tiene este formato" (ej: application/json).
Accept"Quiero que me contestes en este formato."
Authorization"Esta es mi credencial — así sabés quién soy."

El bug clásico: olvidarte del Content-Type

Armás un body en JSON perfecto, pero si no le decís al servidor Content-Type: application/json, muchas APIs no van a saber cómo interpretarlo — y te van a devolver un 400 Bad Request (¿te suena de la Lección 2? el problema es tuyo, no del servidor). No es que tu JSON esté mal escrito: es que nunca le avisaste qué era.

En n8n: el HTTP Request node suele setear Content-Type solo cuando elegís "JSON" como tipo de body. Si armás el body a mano en modo raw, es responsabilidad tuya agregarlo en la pestaña Headers.

Cómo una API sabe quién sos: el header Authorization

La mayoría de las APIs no dejan pasar a cualquiera. Necesitan una prueba de identidad, y esa prueba casi siempre viaja en el header Authorization. Los dos esquemas que vas a encontrar todo el tiempo:

EsquemaCómo se veIdea
BasicAuthorization: Basic dXNlcjpwYXNzUsuario y contraseña, codificados (no encriptados) en Base64.
Bearer / API KeyAuthorization: Bearer abc123...Un token largo que la API te dio antes, y que "portás" en cada request.

Existen esquemas más elaborados (OAuth2, con su propia danza de redirects) para cuando una app necesita actuar en nombre de un usuario de terceros — eso lo dejamos para más adelante. Con Basic y Bearer ya cubrís la gran mayoría de lo que vas a conectar en n8n.

En n8n: cuando elegís "Basic Auth" o "Header Auth" en el dropdown de Authentication del HTTP Request node, n8n arma este header Authorization por vos — no lo ves, pero es exactamente lo que está pasando. Si ese token vence o está mal, es por eso que la Lección 2 te muestra un 401: literalmente "no sé quién sos".

Ejemplos reales

Tres casos reales que muestran que "cómo se manda la credencial" no es siempre igual — por eso hay que leer la doc de cada API, no asumir.

1. GitHub API — Bearer token en el header
GET https://api.github.com/user
Headers: Authorization: Bearer ghp_xxxxxxxxxxxxxxxx

Así es el caso "de manual": la credencial (un Personal Access Token) viaja en el header Authorization, exactamente como vimos arriba.

2. OpenWeatherMap — la key va en la URL, no en un header
GET https://api.openweathermap.org/data/2.5/weather?q=BuenosAires&appid=TU_API_KEY

Este caso rompe la regla a propósito: OpenWeatherMap no usa Authorization en absoluto — la API key va como parámetro appid en la propia URL. No es más ni menos "correcto", es una decisión de esa API en particular. Si asumís que "la auth siempre va en un header" te vas a trabar cuando te encuentres con esto.

3. JSONPlaceholder — Content-Type obligatorio en el POST
POST https://jsonplaceholder.typicode.com/posts
Headers: Content-Type: application/json; charset=UTF-8
Body: { "title": "mi primer post", "body": "probando POST", "userId": 1 }

Es el mismo ejemplo de la Lección 1 — ahora mirando el header que lo hace funcionar. Si lo probaste en n8n sin este header, es probable que hayas visto un 400 de la Lección 2 en vez del 201 esperado.
