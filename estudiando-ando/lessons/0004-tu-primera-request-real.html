Lección 4 · HTTP y APIs

De la documentación a tu primera request real

Ya sabés elegir método, leer un status code y entender headers/auth por separado. Hoy lo hacés todo junto, de punta a punta, con una API real — vos apretando el botón.

Esta lección se hace, no se lee. Vas a necesitar 5 minutos y una de estas dos herramientas: n8n (el HTTP Request node que ya conocés) o la consola del navegador (F12 → pestaña Console). Elegí la que tengas más a mano.

Repaso antes de arrancar

Repaso — Lección 2
Vas a pedir el post con id 9999 en una API que solo tiene 100 posts. ¿Qué categoría de status esperás?
Repaso — Lección 3
Armás un POST con body en JSON pero te olvidás del header Content-Type. ¿Qué status es más probable?

Paso 1 — Leer la documentación (así sea mínima)

Antes de tocar nada, así es la "doc" de la API que vamos a usar hoy, JSONPlaceholder — pensada exactamente para practicar esto sin romper nada real:

Doc resumida
Base URL: https://jsonplaceholder.typicode.com
Recurso: /posts
Métodos soportados: GET, POST, PUT, PATCH, DELETE
Body esperado (POST/PUT/PATCH): { "title": string, "body": string, "userId": number }
Auth: ninguna

Esto es exactamente lo que vas a buscar en la doc de cualquier API real: la URL base, qué métodos acepta cada recurso, qué forma tiene el body, y si pide autenticación. Con esos cuatro datos ya podés armar la request sin adivinar nada.

Paso 2 — Armar el POST

Opción A — n8n: arrastrá un HTTP Request node y configurá:

  1. Method: POST
  2. URL: https://jsonplaceholder.typicode.com/posts
  3. Body Content Type: JSON
  4. Body: { "title": "mi primer post", "body": "probando POST", "userId": 1 }

Al elegir "JSON" como tipo de body, n8n pone el header Content-Type por vos — es la Lección 3 trabajando en segundo plano.

Opción B — consola del navegador: abrí cualquier pestaña, F12, pestaña Console, y pegá:

fetch('https://jsonplaceholder.typicode.com/posts', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ title: 'mi primer post', body: 'probando POST', userId: 1 })
})
  .then(r => r.json())
  .then(console.log)

Acá el Content-Type lo escribís vos a mano — mismo concepto, sin la ayuda automática de n8n.

Antes de ejecutar: ¿qué status code esperás? (clic para revelar)

Debería darte 201 Created — estás creando un recurso nuevo con POST. El body de la respuesta te va a devolver lo mismo que mandaste, más un id nuevo (probablemente 101). Ejecutalo ahora y confirmá.

¿Dónde queda ese post? En ningún lado. JSONPlaceholder es una API "de mentira": contesta como si hubiera creado el post (201 + un id), pero no guarda nada. Lo que ves en el output del nodo es la respuesta del servidor — eco de lo que mandaste más un id — y vive solo en los datos de esa ejecución de n8n. Si ejecutás el nodo otra vez, manda un POST nuevo y recibís de nuevo id: 101. Comprobalo: un GET /posts/101 te da 404. En una API real, el servidor lo guardaría en su base de datos y ahí sí lo podrías volver a pedir.

Paso 3 — Ahora un GET, y un caso que falla

Probá estas dos, en n8n o con fetch (con method GET no hace falta body ni Content-Type):

GET que existe
GET https://jsonplaceholder.typicode.com/posts/1
GET que no existe
GET https://jsonplaceholder.typicode.com/posts/9999
¿Qué esperás de cada uno?

El primero: 200 OK con el post 1 en el body. El segundo: 404 Not Found — no existe un post con ese id. Es el mismo patrón que viste con el repo inexistente de GitHub en la Lección 2, ahora con otra API.

Desafío — hacelo vos, sin la guía

Con lo que ya sabés, resolvé esto sin que te lo desglose paso a paso: hacé un PATCH a https://jsonplaceholder.typicode.com/posts/1 cambiando solo el campo title a lo que quieras. Pensá: ¿por qué PATCH y no PUT acá? (Lección 1). ¿Qué status esperás si sale bien? (pista: no es 201 — eso es exclusivo de crear con POST).

Chequeo del desafío
Hiciste PATCH a /posts/1 cambiando solo el título y salió bien. ¿Qué status esperás?
Idempotencia, de vuelta
Imaginá que el POST del Paso 2 fuera contra una API real (una que sí guarda datos, no JSONPlaceholder) y lo repetís tres veces seguidas, exactamente igual. Según lo que viste en la Lección 1 sobre idempotencia de POST, ¿cuántos recursos "nuevos" se crean?
Por qué importa esto último: es la razón real por la que en n8n hay que tener cuidado con reintentos automáticos en nodos POST — un timeout seguido de un reintento puede duplicar un pedido de verdad. Con GET, PUT o DELETE, reintentar es seguro.
Contame qué status codes te dio cada paso — si algo no coincidió con lo esperado, es la mejor oportunidad para ver por qué (a veces el motivo es más interesante que si hubiera salido bien a la primera).
