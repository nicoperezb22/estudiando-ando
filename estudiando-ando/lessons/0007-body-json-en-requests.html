Lección 7

El body de la request: mandar datos en POST / PUT / PATCH

Hasta ahora viste qué método usar (GET/POST/PUT/PATCH/DELETE), qué te devuelve el servidor (status codes) y cómo te identificás (header Authorization). Falta la pieza que completa un POST o un PUT: el body — los datos que vos le mandás al servidor, no al revés.

Regla rápida: si el método es GET o DELETE, normalmente no hay body — los datos van en la URL (query params) o en el path. Si es POST, PUT o PATCH, el body es donde vive la información que estás creando o modificando.

1. El body no es texto libre, es un contrato

El body es una cadena de bytes. Nada más. Para que el servidor sepa cómo leerla, necesita el header Content-Type que ya viste en la Lección 3 — casi siempre application/json en APIs modernas. Sin ese header, el servidor puede interpretar mal el body o rechazarlo directamente (ese es justo el bug que la Lección 3 nombraba como "clásico"). 

POST /posts HTTP/1.1
Host: jsonplaceholder.typicode.com
Content-Type: application/json

{
  "title": "foo",
  "body": "bar",
  "userId": 1
}

Tres partes, siempre en ese orden de responsabilidad:

  • Método (POST) → decide la acción.
  • Header Content-Type → declara el formato del body.
  • Body → los datos, en ese formato.

2. Caso real 1 — JSONPlaceholder (API pública de prueba)

JSONPlaceholder es una API falsa hecha para practicar sin romper nada real. Un POST a /posts con el body de arriba te devuelve 201 Created y el mismo objeto con un id nuevo — el servidor no lo guarda de verdad, pero simula el ciclo completo.

3. Caso real 2 — GitHub API (crear un issue)

Para crear un issue con la GitHub REST API mandás: 

POST /repos/OWNER/REPO/issues HTTP/1.1
Authorization: Bearer TU_TOKEN
Content-Type: application/json

{
  "title": "Bug en el flujo de lista de espera",
  "body": "Descripción del problema...",
  "labels": ["bug"]
}

Notá que acá el Authorization (Lección 3) y el Content-Type conviven en la misma request — no son alternativas, son headers independientes que casi siempre viajan juntos en un POST autenticado.

4. Aplicado a n8n (tu caso real, FastPass)

En el HTTP Request node de n8n: pestaña Body → activás Send Body → Body Content Type: JSON → elegís Using Fields Below (armás campo por campo, n8n arma el JSON solo) o Using JSON (escribís el JSON crudo vos, útil si necesitás anidar objetos o arrays). n8n agrega el header Content-Type: application/json automáticamente cuando elegís Body Content Type: JSON — por eso en n8n rara vez ves ese bug de la Lección 3, el nodo lo previene por vos.
