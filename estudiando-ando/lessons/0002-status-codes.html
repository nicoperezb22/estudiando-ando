Lección 2 · HTTP y APIs

Status codes: leer la respuesta

Cuando un HTTP Request node de n8n falla, lo primero que te muestra es un número de 3 dígitos. Ese número ya te dice de quién es el problema — antes de que abras nada más.

En la Lección 1 vimos que toda response trae un status code. Hoy nos metemos ahí: qué significa cada rango, y por qué distinguirlos te ahorra horas de debugging mal enfocado.

La regla de oro: el primer dígito

No hace falta memorizar los ~60 códigos que existen. Con saber qué significa el primer dígito, ya podés triangular el 90% de los casos:

RangoSignifica
2xxÉxito. Salió como pediste.
3xxRedirección. "Eso que buscás está en otro lado." (poco frecuente al consumir APIs)
4xxProblema del lado cliente — vos (o tu request) mandaron algo mal.
5xxProblema del lado servidor — no es tu culpa, algo se rompió del otro lado.
Por qué importa distinguir 4xx de 5xx: si tu HTTP Request node en n8n tira un 4xx, el error está en lo que vos armaste (URL, body, token, permisos) — revisá tu request. Si tira un 5xx, podés reintentar más tarde o avisar que la API de terceros está caída; no hay nada que arreglar de tu lado.

Los códigos que vas a ver todo el tiempo

CódigoQué te está diciendo
200 OKSalió bien, acá está lo que pediste.
201 CreatedSe creó el recurso (típico después de un POST exitoso).
204 No ContentSalió bien, pero no hay nada para devolver en el body (típico después de un DELETE).
400 Bad RequestTu request está mal formada — JSON roto, falta un campo obligatorio.
401 UnauthorizedNo te identificaste, o tus credenciales/token son inválidos.
403 ForbiddenTe identificaste bien, pero no tenés permiso para esto.
404 Not FoundEse recurso (ese ID, esa URL) no existe.
409 ConflictChoca con el estado actual del recurso (ej: ya existe algo con ese nombre).
429 Too Many RequestsEstás mandando requests más rápido de lo que la API permite.
500 Internal Server ErrorSe rompió algo del lado del servidor, genérico.
502 / 503El servidor está caído, sobrecargado, o en mantenimiento.
401 vs. 403 — la confusión más común: 401 es "no sé quién sos" (token ausente, vencido o inválido). 403 es "sé quién sos, pero no podés hacer esto" (tu usuario no tiene permiso). Si en FastPass el token de Gmail expiró, vas a ver 401 — no 403.

Ejemplos reales

Estos son casos reales de APIs públicas — probá el primero vos mismo.

GitHub API — repo que no existe
GET https://api.github.com/repos/n8n-io/repo-que-no-existe
↓
Response
Status: 404 Not Found
Body: { "message": "Not Found", "documentation_url": "https://docs.github.com/rest" }

Pegá esa URL en el navegador y vas a ver ese 404 real, con ese mensaje exacto. Así de literal es "el recurso no existe".

La excepción que confirma la regla — rate limiting en GitHub: uno esperaría que "mandaste demasiadas requests" sea 429 (la tabla de arriba dice eso), pero la API de GitHub usa 403 para su límite principal sin autenticación (60 req/hora), y reserva 429 solo para límites secundarios. Esto es a propósito: las categorías (2xx/4xx/5xx) son una convención fuerte, pero el código exacto para un caso puntual lo define cada API — siempre confirmá contra la documentación real, no asumas.

Y del lado del éxito: si probaste el ejemplo de JSONPlaceholder de la Lección 1 (el POST a /posts), el 201 Created que te devolvió es exactamente el mismo patrón que verías creando un pedido real en cualquier API de e-commerce o de pagos.
